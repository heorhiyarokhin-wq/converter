# File Processing — разбор по пунктам (converter)

Рядом: [docs/orm-typeorm.md](orm-typeorm.md), [docs/postgres-sql.md](postgres-sql.md), [docs/auth-authorization.md](auth-authorization.md), [docs/user-profile.md](user-profile.md).

**Важно сразу и честно:** реальной загрузки байтов файлов в converter пока нет. Аватар пользователя — это колонка `users.photo` типа `text`, куда кладётся обычная строка-URL (`https://example.com/avatar.png`). Всё, что ниже — теория плюс чертёж того, как этот же проект вырастет из "URL-строки" в настоящую обработку файлов, если понадобится реальный upload. Каждый раздел явно говорит, что уже есть в коде, а что — блок теории на будущее.

Проверить текущее (единственное реальное) поведение: `requests/user-profile.http`, сценарии с `photo` как URL.

Документация: [Fastify multipart](https://github.com/fastify/fastify-multipart), [MDN FormData](https://developer.mozilla.org/en-US/docs/Web/API/FormData), [IANA MIME](https://www.iana.org/assignments/media-types/media-types.xhtml), [Node streams](https://nodejs.org/api/stream.html), [sharp](https://sharp.pixelplumbing.com/).

## Точка отсчёта: что уже есть в converter

Сущность [`User`](../src/modules/users/entities/user.entity.ts) хранит `photo` как обычный текст:

```ts
@Column({ type: 'text', nullable: true })
photo: string | null;
```

А [`UpdateUserDto`](../src/modules/user-profile/dto/update-user.dto.ts) проверяет только то, что это похоже на ссылку:

```ts
@IsOptional()
@IsUrl()
photo?: string;
```

Запрос выглядит так:

```
PATCH /users/:id
Content-Type: application/json

{ "photo": "https://example.com/avatar-a.png" }
```

Это обычный JSON — `ValidationPipe` (глобальный, из `main.ts`) и `class-validator` прекрасно умеют такое проверять "из коробки". Никакого файла на диск сервер не пишет и не читает — он просто запоминает ссылку, а сами байты картинки браузер потом загружает напрямую с того адреса, который в этой ссылке указан (например, с CDN).

Это сознательно упрощённая модель, а не недоработка: она полностью рабочая для MVP, пока картинки где-то уже лежат (CDN, сторонний загрузчик). Но она принципиально другая по своей природе, чем "настоящая" загрузка файлов — и именно в этом разница между JSON API, который вы уже видели в auth/user-profile, и всем, что описано ниже.

## 1. `multipart/form-data` — почему для файлов нужен другой формат тела запроса

**Проблема, которую решает multipart:** JSON — текстовый формат. Чтобы засунуть бинарные байты картинки внутрь JSON-строки, их пришлось бы закодировать в base64 — а это раздувает размер примерно на треть и требует декодировать всё тело целиком в память перед тем, как начать с ним работать. Для настоящих файлов так не делают.

Вместо этого HTML-формы с `<input type="file">` и большинство API используют формат `multipart/form-data`: тело запроса физически разбивается на **части** (parts), у каждой — свой маленький заголовок (имя поля, для файла ещё и `filename` + `Content-Type`) и своё содержимое. Части идут одна за другой, разделённые случайной строкой-границей (`boundary`):

```
POST /users/aaa/photo HTTP/1.1
Authorization: Bearer …
Content-Type: multipart/form-data; boundary=----NestBoundary

------NestBoundary
Content-Disposition: form-data; name="file"; filename="avatar.png"
Content-Type: image/png

<сырые байты PNG, без кодирования>
------NestBoundary--
```

Сравните это с тем, что реально уходит из вашего фронта сейчас:

```
PATCH /users/aaa
Content-Type: application/json

{"photo":"https://example.com/avatar-a.png"}
```

Второе — просто JSON, `ValidationPipe` его понимает без единой дополнительной настройки. А вот multipart Fastify (HTTP-ядро converter — **не Express**, см. `main.ts`) сам по себе разбирать не умеет — нужен отдельный плагин.

**Важная деталь именно для этого проекта:** в большинстве уроков и статей про Nest встречается `@UseInterceptors(FileInterceptor('file'))` — это обёртка вокруг `multer`, а `multer` работает только поверх Express. В converter адаптер — Fastify (`NestFastifyApplication`), поэтому этот путь не подходит вообще, нужен fastify-нативный пакет:

```ts
// src/main.ts — как ЭТО БЫЛО БЫ зарегистрировано, если бы файлы понадобились
import multipart from '@fastify/multipart';

await app.register(multipart, {
  limits: { fileSize: 2 * 1024 * 1024, files: 1 }, // 2 МБ, один файл за раз
});
```

После регистрации в хендлере файл читается не через `@Body() dto: SomeDto`, а через отдельный API плагина — `request.file()` для одного файла или `request.files()` для нескольких. Обычный `class-validator`-DTO для файла не работает — про это подробнее в разделе про валидацию (§4).

**Практичное архитектурное решение для converter**, если/когда это понадобится: не пытаться протащить и JSON `{photo: url}`, и multipart через один и тот же `PATCH /users/:id` — это два разных формата тела, смешивать их в одном эндпоинте неудобно и на бэкенде, и на фронте. Проще завести отдельный `POST /users/:id/photo` под настоящий файл, оставив существующий `PATCH` для JSON-полей (email, url-фото) как есть.

## 2. File Upload & Download — два разных направления одной задачи

**Upload** — клиент отправляет байты серверу, сервер их куда-то сохраняет и возвращает идентификатор (обычно URL или ключ объекта в хранилище), по которому эти байты потом можно найти.

**Download** — обратное движение: клиент забирает байты обратно. Тут есть два принципиально разных сценария, и их стоит различать:

| Сценарий | Пример | Что уходит в ответе |
|---|---|---|
| Показать прямо в интерфейсе | аватар в `<img>` | `Content-Type: image/png`, без `attachment` |
| Скачать как отдельный файл | выгрузка отчёта | `Content-Disposition: attachment; filename="users.csv"` |

Сейчас download аватара в converter вообще не проходит через ваш Nest-сервер: браузер напрямую обращается по ссылке из `users.photo` к внешнему адресу. Если картинка когда-нибудь будет лежать на вашем собственном диске, появится выбор — либо отдать статику через `@fastify/static` (осторожно: нужна защита от path traversal, о ней в §8), либо стримить файл прямо из хендлера:

```ts
@Get(':id/photo')
@Header('Content-Type', 'image/jpeg')
async getPhoto(@Param('id') id: string, @Res() reply: FastifyReply) {
  const stream = fs.createReadStream(absoluteSafePath);
  return reply.send(stream);
}
```

Обратите внимание на `@Res()` **без** `passthrough: true` — это отличается от того, что вы уже видели в `AuthController`/`UserProfileController` (там `@Res({ passthrough: true })` использовался только для побочного эффекта — выставить cookie, а само тело ответа Nest всё равно формировал сам через `return`). Когда нужно отдать бинарный поток, Nest не должен пытаться сериализовать его как JSON — поэтому берётся "полный" `@Res()`, и ответственность за отправку ответа целиком переходит в ваш код.

**Порядок действий в сервисе имеет значение.** Правильно — сначала проверить права (тот же паттерн self/`update-any`, что уже разобран в `updateProfile`), и только потом писать файл на диск. Если сделать наоборот, получится странная ситуация: файл на сервере уже появился, а клиент получит `403` только на следующем шаге — то есть на диске останется мусор, а в худшем случае злоумышленник, зная схему именования, сможет угадать путь к чужому недавно загруженному файлу.

**Идемпотентность.** Повторная загрузка аватара должна заменять предыдущий файл и обновлять `users.photo`, а не плодить всё новые версии — если только продукт явно не потребует хранить историю аватаров.

## 3. MIME Types — как сервер узнаёт, что именно ему прислали

**MIME-тип** — короткая строка-этикетка, описывающая формат данных: `image/jpeg`, `image/png`, `image/svg+xml`, `text/csv`, `application/json`. У неё есть три возможных источника, и это важно понимать именно в таком порядке — от наименее надёжного к наиболее надёжному:

1. **Заголовок `Content-Type` части запроса** — то, что прислал клиент. Клиент может здесь написать что угодно, в том числе соврать (переименовать `virus.exe` в `photo.png` и заявить `Content-Type: image/png`).
2. **Расширение имени файла** (`.png`, `.csv`) — тоже полностью контролируется клиентом, тоже может врать.
3. **Magic bytes** — несколько первых байтов самого содержимого файла, которые у каждого формата фиксированы (JPEG всегда начинается с `FF D8 FF`, PNG — с `89 50 4E 47`). Это единственный источник, который клиент не может подделать, не сломав сам файл — поэтому для реальной валидации загрузки доверять нужно именно ему, а не заголовку и не расширению.

В текущей JSON-модели аватара (`@IsUrl()`) MIME-тип вообще не участвует в проверке — валидатор смотрит только на то, похожа ли строка на URL, а не на то, что находится по этой ссылке.

Когда появится настоящая загрузка файлов, разумный подход — белый список разрешённых типов (например, только `image/jpeg` и `image/png`), проверяемый по magic bytes, а не по присланному заголовку. SVG стоит здесь особняком — это не просто картинка, а фактически XML с возможностью встроенного JavaScript, поэтому его обычно либо запрещают для пользовательских аватаров вообще, либо подвергают отдельной санитайз-обработке (подробнее в §8 и §12).

Точно так же важно при **отдаче** файла обратно клиенту слать корректный `Content-Type`: если сервер пришлёт SVG с типом `text/html`, браузер может попытаться выполнить его как HTML-страницу — а это уже путь к XSS.

## 4. File Validation — проверки от дешёвых к дорогим

Идея валидации файла та же, что вы уже видели в auth-флоу и профиле (быстрые дешёвые проверки — сначала, дорогие — последними, "guard clauses"), только слоёв здесь больше:

1. **Файл вообще есть** — если нет, `400`, ровно тот же принцип, что и `password is required` в `deleteAccount`.
2. **Размер** — проверяется ещё до того, как файл целиком осядет на диске (см. §5) — иначе можно превратить загрузку в способ забить диск сервера.
3. **MIME + magic bytes** — совпадают между собой и входят в разрешённый список (§3).
4. **Имя файла** — никогда не использовать `filename`, присланный клиентом, как часть пути на сервере: строка вроде `../../etc/passwd` в этом поле — классическая атака path traversal. Правильно — сгенерировать новое имя самому (`uuid + '.jpg'`), полностью игнорируя то, что прислал клиент.
5. **Содержимое** — реально попытаться открыть файл нужным декодером (например, sharp для картинок): битый или обрезанный JPEG таким образом отсекается ещё до того, как попадёт в постоянное хранилище. Для CSV аналогично — парсер с ограничением на число строк/колонок.
6. **Права доступа** — тот же RBAC self/`update-any`, что и у остального профиля: логичнее всего проверять права **до** дорогих операций с файлом (или хотя бы до записи на диск), чтобы не тратить ресурсы на файл, который всё равно будет отклонён по правам.

Прямая аналогия с тем, что уже есть в проекте: `UpdateUserDto` отсекает `"photo": "not-a-url"` ещё на уровне `ValidationPipe`, до того как код вообще доберётся до `updateUser`. Разница в том, что `class-validator` умеет проверять *строки* — а бинарные байты файла таким образом не провалидируешь, эта проверка неизбежно переезжает в сервис (или в отдельный pipe), уже после того как `request.file()` отдал сами байты.

Главный практический вывод: никогда не доверять расширению `.png` в имени файла как единственному доказательству того, что внутри действительно PNG.

## 5. File Size Limits — четыре разных потолка, которые легко перепутать

Здесь стоит явно разложить по полочкам, потому что "ограничение размера" на самом деле означает четыре разные вещи в разных слоях системы:

| Где именно | Что конкретно ограничивает | Как сейчас в converter |
|---|---|---|
| `bodyLimit` в Fastify | размер **всего** тела HTTP-запроса целиком | дефолт Fastify (~1 МБ) — с запасом хватает для JSON-URL, но категорически мало для реального файла-картинки |
| `limits.fileSize` у `@fastify/multipart` | размер **одной части-файла** внутри multipart | плагин пока не подключен вообще |
| Бизнес-правило приложения | "аватар весит не больше 2 МБ" | нет — сейчас в `text`-колонке может лежать URL любой длины |
| `@Throttle` (throttler) | число **запросов** в единицу времени, не байты | уже есть — например, `PATCH /users/:id` ограничен 10 запросами в минуту |

Важно не путать последнюю строку с первыми тремя: throttler защищает от "слишком часто", а не от "слишком много байт за один раз" — это два независимых механизма защиты, и оба нужны одновременно.

При превышении лимита размера файла типичный ответ — `413 Payload Too Large` (либо ошибка на уровне плагина multipart, которую стоит явно превратить в `413`, а не отдавать клиенту сырую ошибку парсера).

Для аватара разумный практический потолок — 1-2 МБ после сжатия. Для CSV-импорта важнее ограничивать не столько байты, сколько число строк: 10 МБ текста в виде компактных строк легко превращается в миллионы записей, и настоящей проблемой становится не память, а процессорное время на обработку каждой строки.

Отдельная деталь именно для текущей JSON-модели: технически ничто не мешает засунуть в `photo` строку с data-URL (base64-картинка прямо внутри JSON) размером в мегабайты — `@IsUrl()` обычно такие строки как раз отклоняет (data-URL не начинается с `http://`/`https://`), но если валидация когда-нибудь ослабнет, это станет незаметной дырой. Общий вывод: base64-картинки в текстовой колонке `text` — плохая идея независимо от размера, потому что они раздувают и таблицу, и любые бэкапы, и каждый обычный `findById`, который эту колонку читает.

## 6. Temporary & Permanent Storage — два разных места хранения файла в его жизненном цикле

Стоит различать, где физически лежит файл на каждом этапе:

**Временное хранилище (temporary)** — файл в промежутке между "байты приняты" и "файл готов лечь в постоянное место": например, `os.tmpdir()` или `/tmp/upload-<uuid>`. Если на этапе обработки (скажем, sharp не смог декодировать картинку) что-то пошло не так — временный файл нужно удалить, а не оставлять висеть на диске навсегда.

**Постоянное хранилище (permanent)** — то место, на которое в итоге ссылается `users.photo`. Здесь есть несколько вариантов с разными компромиссами:

| Вариант | Плюс | Минус | Применимость к converter |
|---|---|---|---|
| Внешний URL (как сейчас) | не нужен ни диск, ни multipart вообще | это не ваш файл — если он исчезнет или изменится на удалённой стороне, вы об этом не узнаете | уже используется |
| Локальная папка `uploads/` на сервере | просто реализовать | нет автоматического бэкапа; если инстансов Nest несколько, они не делят один диск между собой | нормально для разработки, не для продакшена с несколькими инстансами |
| Объектное хранилище (S3/GCS + CDN) | производственный вариант, масштабируется | требует IAM-ключей в конфиге — тот же принцип, что уже применяется к `POSTGRES_*` в `ConfigService` | логичный следующий шаг после локальной папки |

Важная деталь: то, что записывается в базу — это **публичный URL или ключ объекта**, а не абсолютный путь файловой системы вроде `B:\uploads\avatar.png`. Такой путь бессмысленен уже на другой машине или внутри контейнера — там просто нет такого диска.

**Порядок операций при замене аватара имеет значение.** Правильная последовательность: записать новый файл → обновить `users.photo` в базе → только после этого удалить старый файл. Если сделать наоборот (сначала обновить БД, потом записать файл, и запись упадёт) — в профиле окажется ссылка на файл, которого не существует. Здесь важно понимать границу возможностей `@Transactional()` (уже знакомого декоратора из `UsersService.createUser`): он откатывает только SQL-операции внутри одной БД-транзакции. Запись в S3 — это отдельная система, которую транзакция Postgres не видит и откатить не может; согласованность между "файл записан" и "БД обновлена" в таких случаях приходится обеспечивать вручную (например, компенсирующим действием "удалить только что записанный новый файл, если UPDATE не прошёл").

Ещё один практический риск — "осиротевшие" файлы: файл физически лежит на диске/в S3, но в `users.photo` уже стоит другой URL (потому что аватар заменили, а старый файл вовремя не удалился из-за сбоя). С этим борются либо периодической фоновой уборкой, либо простой конвенцией именования (например, имя файла = `userId`, тогда новый аватар автоматически перезаписывает старый физический объект, и сирот не возникает в принципе).

## 7. Streams & Large Files — почему не всё можно грузить в память целиком

**Поток (stream)** — способ обрабатывать данные кусками по мере поступления, а не ждать, пока весь файл целиком окажется в оперативной памяти. Разница принципиальна: `await file.buffer()` для файла на 500 МБ означает, что все эти 500 МБ должны одновременно поместиться в RAM процесса — при нескольких параллельных загрузках это быстро кладёт сервер.

В Node это `Readable`/`Writable`/функция `pipeline` из модуля `stream`. У `@fastify/multipart` часть-файл (`part.file`) уже приходит как поток, который можно сразу же направить в файл на диске:

```ts
await pipeline(part.file, fs.createWriteStream(tmpPath));
```

Когда стриминг обязателен:
- CSV-файлы на десятки мегабайт;
- видео (для аватара не актуально);
- проксирование скачивания файла напрямую с S3 клиенту, без буферизации всего файла целиком на сервере посередине.

Когда буфер в памяти — нормальный и даже более удобный вариант: аватар весом 2 МБ гораздо проще обрабатывать библиотекой sharp прямо как `Buffer`, стриминг здесь избыточен. Правило "всегда используем стримы" не стоит бездумно применять к небольшому PNG в 50 КБ.

Есть прямая параллель с темой N+1-запросов из ORM-документации: выгрузка, скажем, 100 000 пользователей в CSV не должна делаться через `find()` всех строк разом в память — правильный путь такой же, как с постраничным чтением большой таблицы: `QueryBuilder` с ограничением на порцию (или курсор по ключу, а не `OFFSET`, — та же логика "keyset лучше offset на больших объёмах", что разобрана в `docs/user-profile.md`), и запись строк CSV сразу в поток ответа, по мере того как они приходят из базы.

Отдельная деталь: `@fastify/compress`, уже зарегистрированный в [`main.ts`](../src/main.ts), сжимает исходящие **JSON-ответы** — это отдельный механизм, он не заменяет и не отменяет необходимость стримить сам процесс загрузки/выгрузки файла.

## 8. Secure File Processing — специфичные для файлов угрозы поверх уже знакомых слоёв защиты

Многие из этих слоёв защиты вы уже видели на примере auth и профиля — здесь показано, как они переносятся на работу с файлами, плюс несколько угроз, специфичных именно для байтов:

1. **Авторизация (AuthZ)** — та же связка `JwtAuthGuard` + `@RequirePermission('users', 'update')` + self/`update-any`-развилка внутри сервиса, что уже разобрана в `docs/user-profile.md`. Загрузка файла не должна быть публичным эндпоинтом без токена.
2. **Имя файла и путь на диске** — использовать только собственный сгенерированный идентификатор (uuid), никогда напрямую то, что прислал клиент. При сборке абсолютного пути стоит явно проверять, что итоговый путь после разрешения (`path.resolve`) действительно находится внутри разрешённой папки (`resolved.startsWith(uploadRoot)`) — это защита от path traversal, даже если где-то в цепочке случайно просочилось клиентское имя.
3. **Тип файла** — проверка по magic bytes (§3), не по заявленному `Content-Type`.
4. **Размер** — лимиты на всех уровнях из §5, иначе диск сервера можно забить одной загрузкой.
5. **SVG отдельно** — поскольку SVG это XML, внутри него бывает `<script>`; отдавать пользовательский SVG как "просто картинку" без отдельной санитайз-обработки небезопасно. Для аватара практичнее всего просто запретить SVG на входе и принимать только JPEG/PNG.
6. **Явный allowlist форматов** — принимать только то, что прямо разрешено (`image/jpeg`, `image/png`), а не пытаться перечислить всё запрещённое — allowlist почти всегда безопаснее denylist.
7. **Секреты вне репозитория** — сами загруженные файлы никогда не должны попадать в git; конфигурационные секреты (ключи S3 и т.п.) не должны лежать рядом с папкой загрузок.
8. **"Pixel flood" / decompression bomb** — крошечный по размеру файл может объявлять в заголовке огромную ширину и высоту изображения; декодер, доверившись этим числам, попытается выделить гигантский буфер в памяти. У sharp есть возможность ограничить максимальные `width`/`height` ещё до полной обработки — этим стоит пользоваться.
9. **Подмена файла после проверки (time-of-check to time-of-use)** — файл нужно провалидировать, затем атомарно переместить (`rename`) во временную-в-постоянную локацию; недопустимо, чтобы клиент имел возможность дописать содержимое по тому же пути уже после того, как проверка была пройдена.

Логирование этих действий следует тому же принципу, что уже применяется в `[USERS audit]`: фиксируется факт и результат действия (`fields=photo`), но никогда — содержимое самого файла или пароля.

## 9. CSV Parsing — почему это не `split(',')`

**CSV** (Comma-Separated Values) — простой текстовый табличный формат: строки — это записи, поля внутри строки разделены запятой (иногда точкой с запятой), а поля, которые сами содержат запятую, оборачиваются в кавычки:

```
email,role
anna@test.com,user
"Smith, Anna",admin
```

Наивный парсинг вручную через `line.split(',')` ломается именно на такой строке — `"Smith, Anna"` разъедется на два поля вместо одного, потому что наивный сплит не понимает кавычек. Отсюда практическое правило: CSV parsing всегда делается через готовую библиотеку (`csv-parse` для Node, или Papa Parse), которая правильно обрабатывает кавычки, разделители, BOM-маркер в начале файла (`\uFEFF`, который добавляет Excel) и кодировку UTF-8 — а не руками.

Для converter естественный сценарий использования CSV — не импорт целых профилей пользователей (пароли в виде хэша всё равно нельзя восстановить обратно из текстового файла), а массовая выдача ролей: колонка `email` + колонка `role` → запись в таблицу `user_roles` (тот же many-to-many, что уже разобран в SQL-документации).

Практические ограничения: лимит на число строк за один импорт (например, 1000) — иначе один HTTP-запрос может надолго занять event loop обработкой. Ошибки стоит собирать построчно, а не ронять всю операцию на первой же плохой строке: например, строка 14 содержит email, которого нет в базе — разумно либо пропустить именно её и сообщить об этом в ответе, либо (если бизнес-требование — "всё или ничего") откатить всю пачку через уже знакомый `@Transactional()`.

## 10. CSV → JSON — превращение строк файла в типизированные объекты приложения

После того как парсер отработал, на выходе — обычный массив JS-объектов, с которым можно работать так же, как с любым другим входом в приложение:

```ts
type CsvUserRow = {
  email: string;
  role: string;
};

const rows: CsvUserRow[] = parse(csvBuffer, {
  columns: true,          // первая строка CSV становится ключами объекта
  skip_empty_lines: true,
});
```

Дальше на каждую строку имеет смысл прогнать ту же валидацию, что вы уже видели в DTO: `IsEmail()` на email, проверка, что `role` — одно из заранее разрешённых значений (`user`/`admin`), а не произвольная строка из файла. Без этого шага CSV становится каналом, через который в базу может попасть что угодно, включая опечатки и злонамеренный ввод.

Важно не путать это с тем, что сама Postgres тоже умеет работать с JSON (`jsonb`-колонки) — здесь речь о другом уровне: это преобразование строк текстового файла в объекты **внутри вашего Nest-приложения**, ещё до того, как что-либо попадёт в базу. Команда `COPY` в `psql` — это отдельный, гораздо более низкоуровневый путь загрузки CSV прямо в таблицу силами администратора БД, который не проходит ни через ваш HTTP API, ни через какую-либо валидацию приложения.

Разумный ответ такого эндпоинта клиенту — не просто "ок" или "ошибка" на весь файл целиком, а отчёт по каждой проблемной строке: `{ accepted: 18, errors: [{ line: 3, message: '...' }] }` — концептуально тот же принцип, что уже применяется к `409 Conflict` при попытке занять чужой email, только здесь ошибок может быть сразу много и по разным строкам одного запроса.

## 11. JSON → CSV — экспорт данных приложения наружу в виде файла

Обратное направление: например, `GET /admin/users.csv`. Источник данных здесь — тот же `listUsers()`/репозиторий, что уже разобран в `docs/user-profile.md`, а не сырой `SELECT *` — иначе в CSV случайно попадёт `password_hash`, чего категорически нельзя допускать. Колонки экспортного файла стоит перечислять явно (`id, email, created_at`), а не полагаться на то, что "и так всё нужное туда попадёт".

Экранирование полей с запятыми и кавычками внутри — та же по духу проблема, что и при парсинге (§9), только в обратную сторону, и решается она точно так же — библиотекой (`csv-stringify`), а не ручной сборкой строки через `join(',')`, потому что ручная сборка почти гарантированно забудет про экранирование в каком-нибудь редком случае.

Для большой выгрузки стоит применить принцип из §7 — не собирать одну гигантскую строку CSV целиком в памяти, а писать построчно сразу в поток ответа.

Правильные заголовки ответа: `Content-Type: text/csv; charset=utf-8` и `Content-Disposition: attachment; filename="users.csv"` — второй явно говорит браузеру "это файл для сохранения", а не "покажи как страницу".

## 12. Image Formats: JPEG, PNG, SVG — чем они принципиально различаются

| Формат | Что это по сути | Годится для аватара? |
|---|---|---|
| **JPEG** | сжатие с потерей качества, рассчитан на фотографии | да |
| **PNG** | сжатие без потерь, поддерживает прозрачность | да, особенно для иконок с прозрачным фоном |
| **SVG** | не растровая картинка, а векторный формат — по сути XML-документ | обычно **нет** на пользовательскую загрузку — тот же риск встроенного `<script>`, что уже разобран в §8 |

Сейчас формат аватара в базе вообще никак не фиксируется и не проверяется — раз `photo` это просто URL, по этой ссылке в принципе может обнаружиться что угодно, хоть HTML-страница, и `@IsUrl()` никак это не отследит.

Отдельно стоит сказать про WebP/AVIF/GIF — это решается отдельным продуктовым выбором, если/когда появится настоящая загрузка. WebP сегодня хорошо сжимает и поддерживается практически всеми современными браузерами. Анимированный GIF как формат аватара разумно запретить сразу — он тяжёлый по весу и обычно не нужен для профиля пользователя.

Ещё один нюанс, специфичный для JPEG: файлы с камеры часто содержат EXIF-метаданные, включая, например, GPS-координаты места съёмки. При серьёзной обработке эти метаданные стоит удалять (в sharp — явно выключить сохранение метаданных при обработке), чтобы случайно не публиковать вместе с аватаром координаты пользователя.

## 13. Image Conversion — приведение загруженной картинки к единому канону

Смысл конвертации — не менять содержимое картинки творчески, а привести её к предсказуемому единому формату и размеру: например, PNG превратить в JPEG, а картинку любого исходного разрешения ужать до фиксированного квадрата (скажем, 256×256).

Зачем это нужно: клиент вполне может прислать фото 4000×3000 пикселей весом 8 МБ, хотя для отображения в интерфейсе профиля нужен максимум небольшой квадратный превью. Эта конвертация обязана происходить **на сервере**, а не полагаться на то, что фронтенд заранее ужал картинку правильно — фронт можно обойти напрямую через API.

Практический смысл в том, чтобы итоговый URL в `photo` всегда указывал на один и тот же, предсказуемый формат (например, всегда `.jpg`) — тогда клиентскому коду, который рисует `<img>`, не нужно ничего угадывать про MIME-тип на лету.

Библиотека для этого — та же, что и для остальной обработки картинок (см. §15). Важная деталь безопасности: конвертацию нельзя делать через вызов внешней утилиты вроде ImageMagick из шелла с именем файла, пришедшим от пользователя, напрямую в команде — это классический путь к command injection.

Если когда-нибудь всё же понадобится принимать SVG и превращать его в растровую картинку — это делается специальным рендерером (например, resvg), а не универсальным image-конвертером; но для профиля пользователя куда проще и безопаснее просто не принимать SVG на входе вовсе.

## 14. Image Validation & Compression — что именно проверяется и что именно сжимается

**Валидация** картинки — это не просто "файл есть", а конкретно: magic bytes соответствуют заявленному формату, декодер способен успешно открыть файл (не битый), ширина и высота не превышают разумный потолок (например, 4096 пикселей — защита от decompression bomb из §8), и получившееся изображение не является пустым/нулевым кадром.

**Сжатие** решает другую задачу — экономию места на диске и скорости последующей отдачи картинки клиенту: например, JPEG с качеством 80% из 100 визуально почти неотличим от оригинала, но весит заметно меньше; PNG можно квантовать по палитре цветов; итоговый размер стороны можно жёстко ограничить (не больше условных 256 пикселей для аватара). Речь не о "художественных фильтрах", а именно об оптимизации веса и скорости.

Правильный порядок операций: **сначала** validate, **потом** resize/compress, **потом** запись во временное место, и только **потом** — сохранение в постоянное хранилище и обновление `users.photo` в базе. Это тот же по духу принцип "сначала все проверки, только потом побочный эффект", что уже применялся в OTP-флоу (`docs/auth-authorization.md`, `docs/user-profile.md`) — сначала убедиться, что всё корректно, и только затем менять состояние системы.

Если декодер картинки падает на битом файле, это должно превращаться в обычный `400 Bad Request` с понятным сообщением клиенту — а не в `500` с сырым стектрейсом библиотеки внутри тела ответа, тот же принцип, что уже применён к перехвату unique-violation Postgres, превращённому в аккуратный `409`.

## 15. Image Processing Libraries — чем в итоге реализуются §12-14

В `package.json` converter сейчас нет ни одной библиотеки для обработки изображений — раздел ниже описывает, что стоило бы добавить, когда/если появится реальная загрузка файлов:

| Библиотека | Для чего нужна | На что обратить внимание |
|---|---|---|
| **sharp** | ресайз, конвертация между JPEG/PNG/WebP, работа с потоками, быстрая нативная реализация | де-факто стандарт для Node; требует нативный бинарник, значит нужно не забыть про него в Docker-образе |
| **jimp** | то же самое, но написана целиком на JS | проще устанавливается (нет нативных зависимостей), но заметно медленнее — не лучший выбор под нагрузку |
| **file-type** | определение MIME-типа по magic bytes | хорошо закрывает именно §3-4 |
| **dompurify + jsdom** | санитайзинг SVG, если всё же решите его принимать | тяжёлая, не самая простая в поддержке ветка кода — часто разумнее просто запретить SVG на входе (§12) |

Не стоит тянуть в проект тяжёлые библиотеки вроде OpenCV ради обработки аватара — это сильно избыточно для задачи "ужать и сконвертировать картинку профиля". То же касается `canvas` — без явной необходимости в сложной отрисовке она не нужна в бэкенд-коде Nest.

Если этот функционал появится, для конфигурационных значений вроде максимального размера файла и максимальной стороны картинки в пикселях естественно завести переменные окружения по уже знакомому в проекте ритуалу: добавить поле в `config.types.ts` и соответствующее правило в `config.validation.ts` рядом с уже существующими `POSTGRES_*`/`OTP_*` — то же самое, что уже делалось при добавлении любой новой настройки.

## Сводная шпаргалка: как это соотносится с текущим API

Сегодня в converter реально работает только это:

```
JSON PATCH { photo: url } → ValidationPipe (@IsUrl) → updateUser → users.photo (text)
```

А целиком настоящая загрузка файла — если/когда до неё дойдёт очередь — выглядела бы так (это чертёж, не реализовано):

```
JWT → RbacGuard('users','update') → self | update-any
   → multipart-файл принят (@fastify/multipart)
   → проверка size / MIME / magic bytes / успешный decode
   → sharp: resize + пересжатие
   → сохранение (диск для разработки / S3 в продакшене)
   → UPDATE users.photo = новый публичный URL
   → удаление старого файла
```

CSV-импорт/экспорт ролей — это отдельные административные эндпоинты, никак не связанные с колонкой `photo`; для них разумно отдельное право (например, `users@export` или переиспользование уже существующего `rbac@manage`), а не тот же `read`, что используется для просмотра своего профиля.

И последнее общее правило: не стоит хранить файлы прямо в Postgres как `bytea` без веской причины — это раздувает и обычные бэкапы базы, и любой обычный `findById`, читающий строку пользователя. Текстовая колонка с URL — это как раз правильный "якорь", который со временем может начать указывать на объектное хранилище вместо внешнего CDN, не меняя при этом сам подход.

## С чего начать, если/когда эта фича понадобится по-настоящему

1. Оставить рабочим текущий JSON-путь с URL (или явно пометить как deprecated, когда появится альтернатива).
2. Зарегистрировать `@fastify/multipart` в `main.ts` с явными лимитами размера.
3. Завести `POST /users/:id/photo` с теми же правами доступа, что уже есть у `PATCH /users/:id`.
4. Подключить `file-type` (проверка по magic bytes) и `sharp` (обработка), писать во временную и затем в постоянную папку `uploads/`, добавленную в `.gitignore`.
5. В `photo` в итоге писать не абсолютный путь диска, а публичный URL (`/static/...` или адрес CDN).
6. CSV подключать отдельно, только когда появится реальная задача администраторского импорта — не смешивать эту фичу с аватаром.

Официальные источники, с которых стоит начинать, а не с случайных статей: README `@fastify/multipart`, документация sharp, и только потом — SDK конкретного объектного хранилища. Примеры с multer из большинства туториалов по Nest не подходят напрямую — это Express-паттерн, а в converter HTTP-ядро Fastify.
