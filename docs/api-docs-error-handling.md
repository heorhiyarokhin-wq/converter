## 1. OpenAPI

**Что это.** Машиночитаемая (JSON/YAML) спецификация REST API: какие есть эндпоинты, какие параметры/тело принимают, что возвращают, какие коды ошибок возможны, как устроена аутентификация. Не текст для человека — контракт, который можно скормить инструменту.

**Зачем это отдельная сущность, а не просто написать доку руками** (как `docs/*.md` в этом проекте): текст в markdown читает только человек и может незаметно разойтись с реальным кодом. OpenAPI-спецификация — либо генерируется из кода (тогда не может разойтись с реальностью по построению), либо используется инструментами: автогенерация клиентского SDK на фронтенде, автогенерация интерактивной страницы документации (см. §2), contract-тестирование (проверка, что реальные ответы сервера соответствуют заявленной схеме).

**В проекте:** нет ни файла спецификации, ни генератора. Роль "контракта для человека" сейчас выполняют `docs/*.md` и `requests/*.http` — рабочие, но не машиночитаемые и требующие ручной синхронизации с кодом при каждом изменении.

## 2. Swagger

**Что это и как соотносится с OpenAPI.** Исторически Swagger — набор инструментов, из спецификации которого выросла OpenAPI (Swagger 2.0 → OpenAPI 3.0, тот же формат, новое имя). Сегодня "Swagger" на практике чаще всего означает конкретно **Swagger UI** — интерактивную HTML-страницу, которая рендерит OpenAPI-спецификацию в браузере: список эндпоинтов, разворачиваемые схемы запроса/ответа, кнопка "Try it out" прямо из браузера.

**В NestJS** пакет `@nestjs/swagger` делает две вещи разом: по декораторам на контроллерах/DTO генерирует OpenAPI JSON, и через `SwaggerModule.setup(...)` поднимает саму страницу Swagger UI по выбранному пути (обычно `/api` или `/docs`):
```ts
// src/main.ts — как ЭТО БЫЛО БЫ подключено (не реализовано)
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';

const config = new DocumentBuilder()
  .setTitle('Converter API')
  .setVersion('1.0')
  .build();

const document = SwaggerModule.createDocument(app, config);
SwaggerModule.setup('docs', app, document); // страница на /docs
```

**В проекте:** не подключено. Ручной аналог того же назначения ("посмотреть, что умеет API, и попробовать вживую") — файлы `requests/*.http`, которые вы уже используете для ручного тестирования каждой фичи.

## 3. Request / Response Documentation

**Суть.** Для каждого эндпоинта декларативно описать: что принимает (тело, query, path-параметры), что возвращает при успехе, какие коды ошибок возможны. В `@nestjs/swagger` это делается декораторами прямо над методом контроллера, рядом с самим кодом — не в отдельном файле, который легко забыть обновить:
```ts
// как ЭТО БЫЛО БЫ на PATCH /users/:id (не реализовано)
@ApiOperation({ summary: 'Обновить профиль пользователя' })
@ApiParam({ name: 'id', description: 'UUID пользователя' })
@ApiResponse({ status: 200, description: 'Профиль обновлён', type: UserProfileView })
@ApiResponse({ status: 403, description: 'Чужой профиль без update-any, либо self пытается сменить email' })
@ApiResponse({ status: 404, description: 'Пользователь не найден' })
@Patch(':id')
updateProfile(...) { ... }
```
Ключевая идея: документация живёт **рядом с кодом, который её должен подтверждать** — легче заметить рассинхрон при code review, чем если бы описание кодов ошибок жило в отдельном markdown-файле.

**В проекте:** ровно это назначение ("какие коды ошибок для какого роута") уже выполняют таблицы "Ошибки" в `docs/auth-authorization.md`/`docs/user-profile.md`/`docs/file-processing.md` и комментарии в `requests/*.http` — тот же контент, что дал бы `@ApiResponse`, просто не в машиночитаемой форме.

## 4. DTO Documentation

**Суть.** Описать не только сам эндпоинт, но и форму данных внутри тела запроса/ответа — на уровне отдельных полей DTO:
```ts
// как ЭТО БЫЛО БЫ на RegisterDto (не реализовано)
export class RegisterDto {
  @ApiProperty({ example: 'user@example.com', description: 'Email пользователя' })
  @IsEmail()
  email: string;

  @ApiProperty({ example: 'Passw0rd', minLength: 8, maxLength: 72 })
  @IsString()
  @MinLength(8)
  password: string;
}
```
**Важный нюанс, который часто упускают:** `@nestjs/swagger` умеет работать в двух режимах. Либо вручную дублировать `@ApiProperty(...)` рядом с каждым `@IsEmail()`/`@MinLength()` (как выше) — оба декоратора описывают почти одно и то же дважды. Либо включить **CLI-плагин** (`compilerOptions.plugins` в `nest-cli.json`), который на этапе компиляции сам генерирует большую часть `@ApiProperty()` из уже существующих TS-типов и `class-validator`-декораторов, без ручного дублирования — предпочтительный вариант для проекта, где DTO уже щедро аннотированы `class-validator`, как здесь.

**В проекте:** DTO уже полностью описаны через `class-validator` (`RegisterDto`, `UpdateUserDto`, `ConvertFileDto` и т.д., подробно разобраны в `docs/auth-authorization.md`/`docs/user-profile.md`) — при подключении Swagger с CLI-плагином документация полей появилась бы почти бесплатно, без переписывания DTO.

## 5. Authentication in Swagger

**Суть.** Swagger UI по умолчанию не умеет "войти в систему" — но раз большинство эндпоинтов в этом проекте защищены `JwtAuthGuard`, без явного объявления схемы аутентификации кнопка "Try it out" на защищённых роутах будет получать `401`. Решение — объявить схему один раз глобально и пометить, какие роуты её используют:
```ts
// как ЭТО БЫЛО БЫ (не реализовано)
const config = new DocumentBuilder()
  .addBearerAuth() // регистрирует схему "Bearer <JWT>"
  .build();
```
```ts
@ApiBearerAuth() // на контроллере/методе — "здесь нужен токен"
@Controller('users')
export class UserProfileController { ... }
```
После этого в Swagger UI появляется кнопка "Authorize", куда один раз вставляется access-токен — дальше он автоматически прикладывается ко всем запросам "Try it out" на роуты, помеченные `@ApiBearerAuth()`.

**В проекте:** ручной аналог — то, что вы уже делаете руками в `requests/*.http`: логин первым запросом, `client.global.set("userAToken", response.body.accessToken)`, и дальше `Authorization: Bearer {{userAToken}}` в каждом следующем запросе того же файла — концептуально та же идея (один раз получить токен, переиспользовать), просто через переменные REST Client, а не через Swagger UI.

## 6. HTTP Error Codes

Коды, которые уже реально используются в проекте, и их точная семантика (не "просто число", а что именно оно сообщает клиенту):

| Код | Значение | Где в проекте |
|---|---|---|
| **400** Bad Request | Запрос сам по себе некорректен (невалидные данные, битый синтаксис файла) | `ValidationPipe`, `FileTransformService.convert()` при ошибке парсинга |
| **401** Unauthorized | Не удалось установить, кто вы (нет/невалиден токен) | `JwtAuthGuard` |
| **403** Forbidden | Известно, кто вы, но именно это действие вам запрещено | `RbacGuard`, self/any-проверки в сервисах |
| **404** Not Found | Ресурса с таким id не существует (или недостаточно прав, чтобы вообще узнать о его существовании — см. ниже) | `UserProfileService.getProfile`, `FileTransformService.getHistoryForDownload` |
| **409** Conflict | Запрос корректен, но конфликтует с текущим состоянием (email уже занят) | `AuthService.register`, `UserProfileService.updateProfile` |
| **413** Payload Too Large | Тело/файл превышает допустимый размер | `FileTransformService.assertSizeAllowed` |
| **415** Unsupported Media Type | Формат/тип содержимого не поддерживается | `detectFormatByExtension` в `FileTransformController` |
| **429** Too Many Requests | Превышен лимит частоты запросов | `@Throttle(...)`, resend-cooldown в OTP-флоу |
| **500** Internal Server Error | Непредвиденная ошибка на сервере, не вина клиента | Дефолтный fallback Nest, см. §9 |

**Тонкость, уже применённая в этом проекте:** для `getHistoryForDownload` и self/any-проверок иногда `404` используется вместо `403` **намеренно** — чтобы не подтверждать сам факт существования чужого ресурса (тот же принцип, что и "не раскрывать, существует ли email" при логине — единое `401 Invalid credentials` вместо разных ответов на "нет такого email" и "неверный пароль").

## 7. Exception Filters

**Суть.** В Nest исключение, брошенное где угодно в цепочке обработки запроса (guard, pipe, controller, service), в итоге долетает до **фильтра исключений** — компонента, который решает, как это исключение превратить в HTTP-ответ (код, тело). По умолчанию Nest уже использует встроенный глобальный фильтр — именно он превращает `throw new ForbiddenException()` в ответ `403` с телом `{statusCode, message, error}`, без единой строчки кода в проекте под это.

Кастомный фильтр пишется через `@Catch()` + интерфейс `ExceptionFilter`:
```ts
// как ЭТО БЫЛО БЫ — фильтр-пример, ловящий вообще всё (не реализовано)
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const reply = ctx.getResponse<FastifyReply>();

    const status = exception instanceof HttpException
      ? exception.getStatus()
      : 500;

    reply.status(status).send({
      statusCode: status,
      message: exception instanceof HttpException
        ? exception.getResponse()
        : 'Internal server error', // НЕ отдаём message непредвиденной ошибки клиенту
    });
  }
}
```
**Зачем вообще писать свой**, если дефолтный уже что-то делает: чтобы **изменить форму** ответа под единый стандарт всего API (см. §8), залогировать исключение централизованно перед ответом (одна точка вместо разбросанных `try/catch` по всем сервисам), или добавить контекст в ответ (например, `path`/`timestamp`, которых в дефолтном формате Nest нет).

**В проекте:** кастомного фильтра нет — используется дефолтный. Похожая идея централизации уже применяется, но не через фильтр, а через единообразные `[AUTH audit]`/`[USERS audit]`/`[RBAC audit]`/`[CONVERT audit]` логи внутри каждого сервиса (разобрано в `docs/auth-authorization.md`, `docs/user-profile.md`).

## 8. Standard Error Response Format

**Что реально возвращает Nest сейчас** (проверено вживую в этой же сессии, не гипотеза):
```json
{ "message": "Conversion failed", "error": "Bad Request", "statusCode": 400 }
```
Это дефолтный формат `HttpException` в Nest — три поля, без вариаций между разными частями приложения (что уже само по себе некоторая "стандартизация", просто не написанная явно).

**Более развёрнутый вариант**, который встречается в других API (не реализован здесь):
```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "targetFormat must be one of: csv, json, xml, yaml",
    "path": "/convert",
    "timestamp": "2026-09-18T10:00:00.000Z"
  }
}
```
Плюсы такого формата: машиночитаемый `code` (клиент может ветвиться по коду, а не парсить текст `message`, который может измениться при локализации), `path`/`timestamp` полезны при разборе инцидентов. Минус — требует кастомного `ExceptionFilter` (§7) на каждый ответ, лишний слой поверх того, что Nest уже даёт бесплатно.

**В проекте:** используется дефолтный формат Nest без изменений — для текущего масштаба проекта разумно (нет фронтенда, который бы ветвился по машиночитаемому `code`), но это первое, что пришлось бы стандартизировать при появлении, например, мобильного клиента с локализацией сообщений об ошибках.

## 9. Centralized Error Handling

**Главная архитектурная мысль этого пункта:** есть большая разница между "у каждого сервиса свой `try/catch`, который решает, как выглядит ошибка" и "есть одно место, которое решает это для всего приложения". Пример из уже написанного кода — `FileTransformService.convert()`:
```ts
try {
  // ...
} catch (error) {
  await this.historyRepository.save(/* ... status: 'error' ... */);
  throw new BadRequestException('Conversion failed');
}
```
Здесь `try/catch` — не про формат HTTP-ответа (это по-прежнему решает дефолтный глобальный фильтр Nest), а про **побочный эффект** (записать в историю) перед тем, как передать управление дальше тем же самым центральным механизмом. Это уже частичная централизация: единая точка, которая решает "как эта ошибка выглядит для клиента" — глобальный фильтр Nest, а не каждый контроллер по отдельности.

**Важный факт, который часто получают неверно из туториалов:** дефолтный глобальный обработчик Nest **уже** не отдаёт клиенту сырое сообщение непредвиденной (не `HttpException`) ошибки — для любого исключения, которое не является `HttpException` (например, необработанный `TypeError` где-то внутри сервиса), Nest сам логирует полную ошибку на сервере, но клиенту отдаёт безопасный дефолтный `{"statusCode":500,"message":"Internal server error"}`, не стектрейс и не текст исходной ошибки. То есть базовый уровень защиты от утечки внутренних деталей ошибки уже есть **бесплатно**, без единого кастомного фильтра — кастомный `ExceptionFilter` нужен не для того, чтобы "перестать течь", а для более тонких вещей: единый JSON-конверт (§8), централизованное логирование в одном месте, или обогащение ответа контекстом.

**В проекте:** централизация есть на уровне "единообразный паттерн `[MODULE audit]`-логов + единые сообщения об ошибках, не раскрывающие лишнего" (`Invalid credentials`, `Invalid or expired code` — везде одинаковый текст для разных внутренних причин отказа), но нет отдельного `ExceptionFilter`, который бы это формализовал в одном файле — сейчас это достигается **конвенцией** (одинаковый стиль кода в каждом сервисе), а не одним обязательным для всех местом в коде.
